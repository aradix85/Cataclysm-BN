# Cataclysm: Bright Nights — Self-Voicing Accessibility Layer (NVDA)

**This document is the project.** Roadmap and specification in one file, read from disk at the start of each session; assume no other context exists.

**It is a working instrument for a fresh session with no memory, and no human reads it.** Not an essay, not a report, not an archive. Only what is true now, and only what changes what the next session does.

**So when editing it, write the rule and not the story.** A decision that has been made reads as a rule.

- Instead of: *"Braille was a side output until the owner changed it on 2026-08-04; an earlier version of this row claimed the two forms should differ."*
- Write: *"Braille is a first-class channel. Speech and braille carry the same text; a different braille form is the exception and needs a reason at the call site."*

Anything whose subject is this document's own history belongs nowhere in it — a date on a decision, what a passage said before, who changed what and when. The same goes for anything that has to be re-derived from source when it is used: name where it lives instead of copying it, because a copy only rots. `werk\check-doc.ps1` catches the usual forms.

**Never run a formatter over this file.** It is edited and formatted by hand. `deno fmt` belongs to the clone, and let loose here it rewraps every paragraph into a file four times as long, swaps the emphasis marks, pads every table and can break a sentence into a block quote. The cost is not the formatting but the diff: the actual change becomes unfindable. If it happens anyway, `--prose-wrap=never` undoes the rewrapping and the rest is repaired by hand against `git show HEAD:`. **`deno.jsonc` at the project root excludes everything there**, so the tool run from this folder now formats nothing at all; the rule stays because the clone's own config sits one level down and knows nothing about this file.

# THE GOAL, AND HOW IT IS JUDGED

**The fork is the product.** It goes into the mainstream lists of accessible games as a build a blind player downloads and plays. Upstream adopting any of it is welcome and is not the point.

**The target is depth, not coverage.** A blind player should reach the same game a sighted player reaches: the same systems, the same choices, the same wiki, the same guides. Hearing everything is not the same as playing — a recipe list that reads out in full is completely accessible and completely unusable, which is what F5 is about. So the layer is judged by what she can do, never by how many strings it emits.

**The measure is the milestones under `THE PLAN`.** Each is a thing a player does, unaided, from a fresh download. **A milestone is met when she uses the thing for its own purpose once and says what she thinks of it** — she opens the door, she builds the character, she types the filter — and not when its code compiles or its screens emit strings.

**She is not playing this game for pleasure, and the work model does not ask her to.** She said so plainly: the project interests her and the game does not, the world reads as dead and depressing. Two things follow, and both are load-bearing. **What is protected**: nobody but her can hear whether a wording works, a green test says nothing about it, and a phase is never signed off by Claude. **What is not asked**: no milestone requires a survival round, an hour of walking, or a session she has to talk herself into. One honest use of the screen, one verdict, and the work moves on. **A phase whose code is built and asserted does not wait to be signed off** — it waits for one use, and if that use never comes because the game is not worth playing, that is a fact about the game rather than a debt of hers.

**Accessibility here is maintenance, not a finish line.** Upstream adds screens; `werk\coverage.py` reports what appeared. A game fully spoken today is not fully spoken in three months, and the drift check is how that stops being invisible.

# HOW THIS DOCUMENT WORKS

**One step per session.** A step is sized to be finishable in a session: verify the source, write code, write tests, format, run tests, update this file. Do not start a second step. If a step will not fit, split it *in this document* before starting.

**Each step carries what it needs.** Source anchors, API signatures and failure modes live inside the step that uses them. Three sections are shared instead, because what is in them is true for every step: `SHARED FINDINGS` for what steers sequencing, `BUILDING` for this machine, `ARCHITECTURE` for where the code lives. Nothing else is a reference section.

**Steps have names.** Numbers give order and change when the plan is reordered; names do not. Refer to a step by name.

**Instruction count is the budget.** Instruction-following degrades across *all* rules as their number grows, so every rule here costs something from every other rule. A rule earns its place only if it changes what a session does and could not be worked out from the source or from ordinary knowledge. Delete one when it stops doing that — but never delete a working rule to make room for another. This is also why `CURRENT` sits at the very end: the start and the end of a long document are the positions followed best.

Bare `bash` resolves to WSL, which is not installed. A command goes through a temporary script file, so quotes survive. The GitHub CLI is logged in as `aradix85`.

A sleep inside a command is therefore safe — the call returns at once and the sleep goes on — and a session survives the conversation, so an expensive build is never lost. The shape is: start it, confirm in the same call that it is running, then poll, say a sentence, poll again.

When behaviour is in question, the game's source settles it and this file does not.

## Testing is not optional

Automated checks are free; the owner's testing time is the scarce resource. Never present something for NVDA testing that a test could have caught. Steps that produce nothing audible are fine — they are covered by tests instead.

**A Lua assertion costs no build; put it where that stays true.** Drop a `*_test.lua` into `tests/lua/bn_access/` and it runs: `tests/bn_access_lua_test.cpp` finds every script there by name, gives each a Lua state of its own, and hands it `check.equal( actual, expected, label )` as a global. The label is what a failure prints, so write what the case proves. A script that asserts nothing fails, and so does an empty folder. **Write a C++ case only when the test is about the bridge** — a value built in C++, handed to Lua and compared against what C++ itself computes. That is upstream's shape in `tests/catalua_test.cpp` and it is right for that job; for logic that is Lua on both sides it buys nothing but a link.

**The layer is loaded into the world the suite builds**, which has two consequences a C++ case has to allow for. Its handlers are registered in the global state, so no hook is ever unregistered there: a case asserting that an idle hook builds nothing must empty that hook's list first, with `test_lua_hooks::emptied_hook`, or it decides by whatever ran before it while still reading correct. And the game's own tests raise real prompts, which the layer answers — which is why the bridge's default sink in a test binary is a recorder rather than NVDA.

Before presenting any step as done:

1. `build-scripts/fmt.sh` — JSON, Lua and Markdown bare; C++ only as `fmt.sh cpp` with the files the fork owns, for the reason below. It is also a pre-commit hook.
2. `werk\build.cmd` — configure, compile, tests. See `BUILDING`.
3. For Lua, the `[lua]` filter and **`werk\luacheck.ps1`** from the project root. It runs the EmmyLua analyser and hands the output to `build-scripts/bn_access_luacheck.py` in the clone, which keeps only `data/access` — the checker walks the whole tree and the rest is upstream's. **One family there is permanent and not a defect: `unresolved-require`.** The analyser resolves a module name the way a mod writes one — dotted, `require("lib.x")`, against the workspace roots — while the layer has to write the path form `require("./lib/x")`: it is loaded by the fork rather than by the mod system, so there is no mod base path to resolve a dotted name against, and writing one makes the engine itself fail to load the layer. **The hook-return warnings are gone rather than tolerated** — the generated annotation named one return type where the engine accepts three, and widening it removed all twenty-three. **Findings are counted, not hidden** — a filter that drops a family also drops the first genuine one — and anything else is printed as a finding, with exit code 1. **The judging lives in the clone because CI runs the same script**; change the rule there, never in two places. **Regenerate the annotations after adding a C++ binding first**, or it judges the new surface against a stale file.

**Formatting on this machine needs one folder prepended, and one tool aimed.** `astyle` and `deno` are on `PATH` for a shell the MCP server started; `clang-format` is not, so prepend `C:\Program Files\LLVM\bin` yourself. `clang-format` handles `tests/` and the subdirectories of `src/`. `astyle` came from `pip install astyle` and handles the top level of `src/` — but **the installed version reformats untouched upstream lines** (`namespace X\n{` collapses to `namespace X {`), so call `build-scripts/fmt.sh cpp` with the files the fork owns rather than bare or with a staged list that includes upstream files. If it rewrites something you did not touch, `git checkout` that file against the index and keep going. **The pre-commit hook runs the same formatter over everything staged, so a commit that carries an upstream file brings that rewriting back**: format the fork's own files by hand first, then commit that one with `--no-verify`, and check `git show --stat` afterwards. `deno` runs `deno fmt`, `deno task dprint fmt` and `deno task docs:gen`. **In Git Bash `deno task dprint fmt` stops on `require is not defined`**, and `fmt.sh` and the pre-commit hook run there, so both exit 1 after `deno fmt` has already run. The dprint that upstream's `deno.lock` pins starts from a CommonJS file; from PowerShell it starts, and a newer Deno does not change that, while a newer dprint would mean diverging from upstream's lock. Format Lua with `deno run -A --unstable-detect-cjs npm:dprint fmt <files>` instead — the same pinned version, so the same result as upstream's — and commit with `--no-verify` after checking `git show --stat`.

**Locally, run the `[lua]` filter and leave the full suite to GitHub.** Pushing to `main` builds and runs the whole C++ suite on Windows and Linux — see `BUILDING`. Run it locally as well only when the answer is needed before pushing.

## Mistakes to avoid

Each of these has been paid for at least once. They are rules, not stories.

- **Measure, do not reason.** Every number here is cheap to obtain again, and upstream changes daily. Re-derive any number before quoting it, and write down what was counted, where, and with which command. Never skip a measurement because the outcome seems obvious.
- **Announcing a long job is not starting it.** Saying a build has been started and not starting it costs the owner the whole waiting time before anyone notices, because she has no window to glance at. **In the same call that starts detached work, confirm it is running** — count the processes, or check that the log file exists and is growing — and say which of the two was seen.
- **Test the instrument before trusting it.** Before reporting anything negative, ask whether the check *could* have returned a positive. A grep may have the wrong pattern; a passing test may never have executed the line it claims to cover. Run a tool as a fresh process from nothing and verify the changed line actually ran. If a check overturns an earlier finding, test the check first; if a result looks too good, suspect the measurement. Record a negative result narrowly: "not found in X" is a result, "does not exist" is a conclusion that needs a stated search space.
- **Changing a file the game reads is not finished until the game has read it.** A settings file rewritten with a byte order mark is silently rejected, every setting reverts to its default, and the first evidence is a screen that does not speak. Write the file, start the program, and confirm its newest session logs no error.
- **Force UTF-8 on anything that writes a file or prints a report.** The legacy code page dies on the first non-ASCII byte, after the work is done.
- **Do not starve context.** Filter inside the script, poll with short commands that print one line, and speak between steps. Never read a progress stream into context.
- **An exciting finding is a reason to re-read the constraints, not to build on it.**

# THE SPEECH SPECIFICATION

This is the product. Every step that produces spoken output is judged against it. Each principle answers a documented failure in CDDA accessibility (GitHub issues #65577, #62075, #55436, PR #72344) reported by blind players — recorded failure modes, not preferences.

## The five failure modes

- **F1 — Interleaving.** CDDA read the option list interwoven with the selected option's description, on six of seven screens. → *One utterance, one subject.*
- **F2 — Selection not announced.** Five screens gave no indication which option was active. Described by the player as a regression: the name used to be spoken first, and when that ordering changed, playability vanished with no feature removed. → P2.
- **F3 — Invisible channels.** Infrared-detected creatures never appeared in the look-around menu, making infrared goggles worthless. The mechanic works; for the blind player it does not exist. → P6.
- **F4 — Leading noise.** Keybinding hints and header summaries read before the content. → *Speak only what was requested.*
- **F5 — Unbounded length.** Recipe lists that take forever; per-tile reading that worked but was exhausting. → *Every utterance is bounded.*

## The nine principles

- **P1 — Layered, not flat.** Three separately requestable levels: *overview* (count and severity), *list* (browsable, one item per utterance), *detail* (one item in full). The player chooses depth; the system never dumps everything.
- **P2 — Name first, always.** Order within an utterance: `<name> — <position> — <status> — <detail>`. Lets the player cut speech off as soon as they know enough.
- **P3 — Relative position, not coordinates.** `<distance> <bearing>` — "four northeast". Eight directions, no degrees.
- **P4 — Grouped, not spatially ordered.** Never grid order. Group by kind, then distance: enemies → NPCs → animals → items → terrain. Enemies first because they are the only category that can kill you immediately.
- **P5 — Silence is information.** Say nothing when there is nothing. No "zero items in view". This holds only while silence has one meaning: the layer says one word when the world is ready, so silence before it is loading and silence after it is a fault.
- **P6 — Extensible detection model.** One collector; channels register themselves. Adding a channel must never require changing the list code.
- **P7 — Priority interrupt.** A warning arriving during a long list cuts it off. An attack must never queue behind an inventory enumeration. **Not built, and deliberately not — see P8 for the condition that would build it.**
- **P8 — The queue is bounded, and stale is worse than incomplete.** Speech queues at NVDA, not in the game, so nothing throttles a producer. **Nothing throttles it today either, and no priority is used: every utterance goes out as it arrives, in the order it happened.** Do not reach for NVDA's `next` to get priority back: it can discard what is already waiting rather than merely overtake it, which is a real cost for no gain while every utterance is one short sentence. Build a queue policy when a real burst proves one is needed, and declare it per producer. Defaults if so: a hard cap on depth; overflow drops the **oldest**; identical utterances inside the window collapse to a count; anything above the current priority clears the queue rather than joining it. Never let the player act on a report of the previous turn.
- **P9 — Re-readability is bought when something is lost, not before.** The layer keeps no scrollback: everything the game says is said as it happens, and nothing is dropped, so there is nothing to recover. **Build the scrollback in the same step that first drops, collapses or delays an utterance** — one buffer, per entry a spoken and a braille form, keys to page back. Never ahead of that. **The measured fact that makes it necessary the moment anything is lost:** in NVDA sleep mode, the mode this project requires, NVDA's own review cursor, repeat command and speech history do not work, so a missed utterance is gone. `brailleMessage` is a flash message, not a readable buffer, so paging would be ours to build regardless.

# FIXED CONSTRAINTS

## Project

| Decision | Rationale |
|---|---|
| **Bright Nights, not Caves of Qud or Dwarf Fortress** | Source access, existing Lua hooks, a small merge-conflict surface. Qud means reverse-engineering a closed binary; DF depends on fragile memory offsets. |
| **Self-voicing, not screen-reader compatibility** | Exposing an accessibility tree is high-effort, low-yield. Self-voicing is what has produced sustained playability elsewhere (Stardew Access, Factorio Access). |
| **NVDA on Windows only** | The only platform the owner can test. Non-Windows compiles the speech layer to a no-op so builds don't break. |
| **No sighted help, ever** | Not a fallback, not once. A plan that needs it is not a plan. |
| **Speech only — no audio layer** | No sound cues, no spatial audio, no stereo positioning. The problem is information *structure*, not *channel*. |
| **Braille is a first-class channel** | She reads braille and treats it as essential. The ordinary way to emit an utterance is `tts::output`, which reaches speech and braille together, so a channel cannot be lost by omission. **Both channels carry the same text**: she reads braille and listens at once, and two forms that can drift apart cannot be checked against each other. The two-string overload is the exception and needs a reason at the call site, for a written form that is a different thing rather than a shorter wording of the same one — "4 NE" beside "four northeast" is not an exception. |
| **Accessible from the first screen, not from the first world** | A build that becomes accessible only after the player has blindly guessed two correct keys is not accessible. This is why the layer is not a mod: mods arrive with a world and die with it, and the screens before and after one are exactly where a player without sight is most stuck. The opening screen, the world picker, the load list and **the screen a world is made on** speak too, whatever that costs. |
| **Stay as close to upstream as the job allows** | Every line the fork differs by is a line that can conflict, and a behaviour that the wiki, the guides and other players describe differently from how it now works. So: use the game's own screens, keys and order rather than building alternatives; keep every edit to an upstream file down to one call into a file of ours; and when a flag, a setting or a structure of ours turns out to buy nothing, put it back the way upstream has it. Divergence has to earn itself, every time. |
| **The fork is the deliverable, upstream adoption is a bonus** | Upstream has not answered issues #8827–#8829 or two discussions. Track A is written to be submittable so the fork can shrink if they ever land; nothing waits on them. |
| **The default mod list is ours, and every entry must earn a blind player something** | It carries the core and the simplifications that mean fewer systems to track and fewer messages to hear. Anything visual or cosmetic is out: a tileset costs load time and shows nothing, and every extra mod is another variable when diagnosing a wrong announcement. Judge an addition by what it gives someone who never sees the screen, not by whether it is harmless. **`bn_lua` is out for a different reason and removes nothing**: no mod in the tree answers to that name, upstream's own list carries it anyway, and the game drops it in silence while building the world. **The owner's own game is a separate list and does not belong in this one**: the game reads `config\default_mods.json` first and only falls back to `data/mods/default.json`, and `config\` is gitignored, so what she plays with stays on her machine without a git trick. That file is her list and it is the longer of the two; read it rather than assuming what is on. **So a mod she is playing with is not in the fork**, which is worth knowing when a name in a report belongs to no mod the fork's own list has. **She also runs mods the clone does not have at all**, installed by hand from the registry into `mods\`, which upstream gitignores — so look a name up in `data/mods` first and in `mods\` second, and take the list itself from `config\default_mods.json` rather than from either folder. |
| **C++ does the wiring, Lua does the behaviour** | BN's Lua sandbox opens only `base`, `package`, `math`, `string`, `table` (the library list in `src/catalua_impl.cpp`) — no `os`, no `io`. Lua can decide what to say but cannot speak. All opinionated logic stays in script, where it survives merges. **This is also the cost model: a Lua change compiles nothing, but it does cost a restart — see `Running and tuning the game on this machine`.** |
| **The tiles build, with ASCII as a display option** | Game sound exists only through SDL, and the layer's key handling was designed and verified on what SDL delivers; on Windows a curses build would also need ncurses, which this CMake route lacks. ASCII in the same build gives a blind player the speed, and her config already uses it. Only about fifteen of the 394 files under `src/` are tile-specific, so a curses build would save little compile time. |

BN is turn-based, which makes self-voicing far easier than for real-time games: no tempo pressure on speech.

## Two-track strategy

Work splits into two kinds with different destinations. Keep them separate from the first commit.

**Track A — generic engine additions.** Hooks and bindings useful to any mod author. Build each as a standalone, self-contained commit; never mix Track A with speech-layer code in one commit or it becomes unsubmittable as a PR. Frame as general capability, not accessibility — which is honest: polling is lossy for any event-reactive mod. Filed: **#8827** (vehicle_part/vpart_info), **#8828** (construction types), **#8829** (`on_add_msg` hook, built — that commit is the PR if it is ever offered), **#10077** with **PR #10078**, both closed as machine-written (the hook cache that cannot hold two Lua states — the fix stays in the fork, and upstream's ground for refusing it is sound: it has no second state), and **PR #10258**, the `HookCallback` annotation widened to the three returns the engine accepts — **merged upstream, so `data/raw/generate_types.lua` is identical to theirs and off the conflict surface**. **Nothing is offered upstream unless the owner writes it herself, in her own words.** A submission that reads as machine-written is closed on sight there, whatever it repairs, and the project states the terms: `.github/pull_request_template.md` requires their headings, the AI-assistance checkbox and an `Assisted-by:` trailer on every assisted commit, and `docs/en/contribute/contributing.md` closes without warning any PR whose summary a person did not write. # SHARED FINDINGS

Verified facts that steer sequencing rather than a single step. Anything belonging to one step lives in that step.

## Which Lua state is alive, and when

The order in `src/main_menu.cpp`, in the branch that starts a game: the world is picked, then `g->setup()` runs, which calls `init::load_world_modfiles`, which builds the Lua state and runs each mod's scripts. Only then comes `pc.create( play_type )`, character creation, and then `g->start_game()`.

**So character creation, the intro and everything after it are inside a world's state**, and need nothing but firing points — ordinary work, the same shape as menus. **The world's state does not outlive the world**: `DynamicDataLoader::unload_data()` ends in `lua.reset()`, so anything registered there is gone the moment a world is left. That is why the layer has a state of its own; a mod cannot, which is why it is not one.

**`cata::startup_lua_test()` is not that state.** It builds one in `main.cpp`, runs `data/raw/on_game_start.lua` — one line, printing "Lua online." — and destroys it on return (`startup_lua_test` in `src/catalua.cpp`). The layer's own state is built beside it; see `ARCHITECTURE`.

**The opening screen is not a `uilist`**, so `on_uilist` will never reach it: `main_menu::opening_screen` builds its own `input_context` with `NEXT_TAB`, `PREV_TAB`, `CONFIRM` and `ANY_INPUT`, and draws itself through `print_menu`. It has a firing point of its own; see `ARCHITECTURE`. Three screens behind it *are* uilists: the character template picker, load character, and manage world.

**A firing point must not gate on the world's Lua state.** `resolve_hook_state` answers with the layer's own state where there is no world, and `has_hooks` and `run_hooks` handle there being no state at all. Testing `DynamicDataLoader::get_instance().lua` instead silences exactly the screens that come before a world, and it does so invisibly — the code reads as a null check.

**But `resolve_hook_state` prefers whichever state has a handler for that hook, the world's when both do.** Preferring the world's outright would silence the whole of data loading: that state exists from the start of the wait and the layer is loaded into it at the end, so a mod failing its API version, a JSON error or a world naming a mod that is gone would stop the game on a blocking prompt with nothing said — inside the silence the layer has just told the player to expect. `pick_hook_state` holds that choice and is asserted without a world.

## Every input loop is a separate place to be reached, and there are three kinds

A command is not "working" once a key produces speech in ordinary play. The game asks for input in three different ways, and a command must be carried into each of them deliberately.

1. **The main loop** — `game::handle_action` via `get_player_input`. Reads the whole registered action list, so an action in the registry works here for free.
2. **The activity poll** — `game::handle_key_blocking_activity` (`src/game.cpp`), which runs ten times a second for as long as an activity runs or the character travels. It builds the same context but then handles a hardcoded five actions and silently drops everything else. **The main loop does not run at all meanwhile**, so without a second firing point a command is dead exactly when the player is waiting and most wants to ask what is happening. Both call sites now fire `on_action`.
3. **Every screen with its own `input_context`** — inventory, crafting, the `main_menu` that `ESC` opens, and every other screen in the game. Our actions are not registered in those contexts and cannot be, one by one. This is the reason a command that answers in the field goes silent the moment any screen is open, and it is what `THE PLAN` is mostly about. **`on_uilist` does not change this**: it lets the layer speak a menu, and it gives no key of ours a way in. Inside a menu, its own keys are the only keys.

**The third kind includes blocking prompts, and those are the dangerous ones.** A `query_popup` such as "You may be attacked! Proceed?" and an NPC dialogue take over the keyboard completely: they accept their own two or four keys and swallow everything else, including every accessibility command. The game raises them unannounced, in the middle of ordinary play. Without sight the result is indistinguishable from a dead keyboard or broken code. **A blocking prompt that does not speak makes every other command unreachable**, which is why prompts were the first thing made to speak.

**So the rule for every new command: say which of the three it reaches, and test it in the state where it matters, not only standing still in a field.** For anything that reports the surroundings or the character's condition, the activity poll is not optional — that is the state the answer is for.

**The hook must ignore the input layer's sentinels.** `handle_input` answers `TIMEOUT`, `ERROR` or `ANY_INPUT` when nothing was pressed or nothing matched. The activity poll produces those ten times a second, so firing the hook on them would call into Lua continuously; `run_on_action_hook` drops them.

**The direction prompt is the largest silent chokepoint left, and it is one function.** `choose_direction` in `src/action.cpp` puts up a `static_popup` — "Jump across where? (Direction button)" — and then runs an `input_context` loop of its own. `on_query_popup` belongs to `query_popup` and never fires there, and the popup is not a `uilist` either, so nothing in the layer reaches it. Around seventy call sites arrive through it, `choose_adjacent` and `choose_adjacent_highlight` together: close, pry, smash, peek, jump, filling a container, and most of what a verb asks "where?" about. **Until one firing point goes into that function, all of them take the keyboard in silence** — which is exactly the shape that reads as a dead keyboard, since her next arrow key is answered by the prompt rather than by the world.

## The map of the job is generated, not remembered

`werk\coverage.py` writes `werk\logs\coverage.md`, and it maps the game from two sides. **The measurement itself lives in the clone** — `build-scripts/bn_access_coverage.py`, with its baseline and its own instrument check beside it — because CI runs it and because a baseline belongs with the code it guards; `werk\coverage.py` is a wrapper passing this machine's paths, so change the measurement there and never in two places. **The screens:** every input context with how many commands it binds in `data/raw/keybindings/`, how many it registers in C++, whether its file builds uilists, and which one the layer reaches; where uilist is built; every hook with its firing points. **The verbs:** every command the player has in the field, with the `ACTION_*` behind it, whether its case body in `handle_action.cpp` speaks or asks, and — resolved one level down, through the file that owns what it calls — whether it opens a screen and which one. **Run it and read that file before planning anything about scale, and never quote a number about size from this document.**

**The verb list is the one to check a milestone against, not the screen list.** A screen count says how much surface exists; the verbs are the game as the player meets it, so "she can wield, eat, reload and drop" is answerable from that table and "the inventory speaks" is not. The signals in it are hints and not verdicts: `speaks` means the body adds a message and therefore already reaches the layer through `on_add_msg`, `asks` means it raises a prompt the layer already speaks, and `opens a screen` names the file when the callee itself owns one and otherwise names the wrapper to read — **beyond one hop the file is a guess and the wrapper is not**, so it says `via avatar_action::eat` rather than pretending to know which screen.

**The verbs that report no signal at all have been looked at, and almost none of them need work.** Eight are the view-shifting commands, plus centring the view, the zone overlay and the debug submap grid: **camera only, nothing a player without sight can perceive and nothing to say.** The two that matter are `action_menu` and `main_menu`, which do open screens; they read as blank because they are handled before the switch that the scan reads, not because they do nothing. So: **treat a blank signal as a question, not as an answer**, and check the case is not one of those two.

**It remembers, so an upstream merge cannot add a screen or a verb unnoticed.** The baseline is `build-scripts/bn_access_coverage_baseline.json` in the clone, beside the measurement itself, and it is committed with the code it guards; every run prints the drift against it: a screen or verb that appeared, one that vanished, one whose command count or signals changed, and the same for hooks. **Run it after every merge and read those lines** — anything listed as new is something the layer does not speak. Accept a reviewed result as the new baseline with `--record`, which is a deliberate act and belongs in the same commit as the merge. The drift detection was checked by corrupting a copy of the baseline and confirming every kind of change was reported.

**One grep for `input_context` undercounts the game by a quarter, so do not count by hand.** A context is built in five shapes: a plain declaration, a constructor initialiser list (the inventory, the vehicle screens, the main menu — all missed by the obvious pattern), a `make_unique`, a `uilist` naming its own `input_category`, and a default argument. `build-scripts/bn_access_coverage_selfcheck.py` keeps the scan honest: it holds the contexts found in source against the categories that bind keys in data, and anything bound in data with no construction found means the scan missed a shape rather than that the screen does not exist. Two names remain unmatched and both are debug data.

Four structural facts from that report steer the plan, and they are stable in a way the counts are not:

- **Every uilist shares one context, `UILIST`, declared in `src/ui.cpp`**, unless a menu overrides `input_category` — a handful do. So one piece of work reaches every uilist menu at once, and their keys are one category rather than hundreds.
- **The vehicle control menu is a uilist too.** It registers no actions of its own: `keybind()` in `src/vehicle_use.cpp` looks a key character up from the `VEHICLE` category and puts it on a `uilist_entry`. A scan for `register_action` therefore shows nothing there while the screen is one of the largest in the game.
- **The message log and blocking prompts are chokepoints, and both are already covered** by one hook each, against thousands of call sites between them. Prefer a chokepoint over an enumeration every time.
- **The game already has a menu of every verb, and it is a uilist.** `action_menu` is bound to `RETURN` in `DEFAULTMODE` and is built from `uilist_entry` in `src/action.cpp`, and **the commands this layer registers are listed in it too** — that is what `cata::lua_action_menu::run_entry` is for. So the menu step does not only open the game's screens: it makes every command in the game reachable without a key of our own.

## Key space, to be re-derived rather than quoted

BN uses vi-style movement (`hjkl`, `yubn`), the number row and the numpad for directions, and every symbol, leaving no free unmodified letters, digits or punctuation. Measured in `keybindings.json`: of the F-row, only **F12** is bound in `DEFAULTMODE`, to `debug`. **The F-row is the whole space a key of ours can live in** — but the ceiling matters less than it looks, because the game's own action menu on `RETURN` already lists our commands, so a command without a key is reachable rather than lost.

The JSON contains no `modifiers` field anywhere, so all chord space appears free — but that proves BN binds no modified keys, not that SDL delivers them. **Verify a chord such as `ctrl+shift+k` in the running game before designing on it.** A single unmodified F-key is preferable for anything pressed dozens of times per session. Measure chords with injected keypresses only as a last resort, and read the rule below before believing any negative result.

## Read the screen rather than asking her what she sees

When something behaves inexplicably, capture the game window with `werk\schermopname.ps1` and look at the image. That turned an unexplained dead keyboard into an obvious answer in seconds three times: a modal "Proceed?" prompt, an NPC dialogue, and the silent language picker. **She cannot describe what she cannot perceive, so asking her to look is asking the impossible; the screenshot is the instrument that closes that gap.** `PrintWindow` with flag 2 captures the window even when another window overlaps it, so it does not need focus, and the script downscales to a JPEG because a full-size capture exceeds the size a tool result may carry.

Do not use full-screen captures: they pick up whatever else is on her desktop, which is hers and not part of the task.

## Do not send synthetic keypresses to test

`keybd_event` and `SendKeys` go to whichever window holds focus, so a stray keystroke lands in her browser or her editor. Worse, the measurement lies: **NVDA's keyboard hook passes injected keys through untouched while it filters physical ones**, so an injected key can succeed where hers fails and prove nothing about her experience. Injected input did confirm one thing worth keeping: it reaches the game when the window truly has focus, which is how the code was cleared of blame. Use it only against a window whose foreground state has just been verified, and never as evidence about what her keyboard does.

## NVDA sleep mode is the right setup, and it does not block our speech

Verified in NVDA source (the controller-client speak handler in `source/NVDAHelper/__init__.py`): it returns early only when the focus object is in `SLEEP_FULL`, an appModule-only state. Ordinary sleep mode (`NVDA+shift+s`) sets `sleepMode = True`, not `"full"`, so text goes through to the speech queue. Braille takes the same path with the same single gate. Measured on this machine: in sleep mode the controller client speaks normally and NVDA's own keys are inert in the game window while still working elsewhere.

Consequences:

- **The whole keyboard is ours inside the game.** NVDA is not a constraint on default keybindings; only BN's own bindings and the owner's keyboard are.
- **NVDA's review cursor, repeat and speech history are inert too.** Hence P9.
- **Speech mode off (`NVDA+s`) is different and dangerous.** `speak()` in `source/speech/speech.py` returns early on `SpeechMode.off`, on the path our text takes. It silences the accessibility layer; sleep mode does not. **Never use `NVDA+s` as a "be quiet" key while playing** — the silence command must use `cancel_speech`.
- Sleep mode is not remembered across NVDA restarts, and **a configuration profile cannot carry it** — sleep mode is an appModule state, not a saved setting. What works is an appModule with `sleepMode = True`, mapped to the executable with `appModuleHandler.registerExecutableWithAppModule` because `cataclysm-bn-tiles` has hyphens and cannot be a Python module name. **Ship it as an ordinary add-on rather than through the developer scratchpad**, which needs a setting enabled and is a development detour: NVDA scans every folder under `%APPDATA%\nvda\addons` at startup, so a folder with `manifest.ini`, `appModules\` and `globalPlugins\` is all it takes. It lives in `addons\bnAccessSleep\` on this machine and is not packaged for anyone else. **An add-on is not how a stranger gets speech** — the controller library ships beside the executable and does that on its own, see `Running alongside the phases`; the add-on only stops NVDA reading the drawn screen over the layer, which is a comfort setting rather than a requirement. **It takes effect only after NVDA restarts**, and `%TEMP%\nvda.log` says whether it was found and which appModule the game got.

## Lua commands cost no game time

After a Lua-dispatched command the game returns `ACTION_NULL` (`handle_action_menu` in `src/action.cpp`), which hits the dummy-entries `break` in the action switch in `src/handle_action.cpp`. No turn passes. Browsing a list, re-reading surroundings and querying anything are free. The same holds for a Lua-owned `input_context` loop, which never returns an `action_id` at all.

**Every interactive screen uses `input_context`**, all following the same shape: construct a context, `register_action` each command, loop on `handle_input()`. The `input_context` binding is therefore not a single-purpose tool; it is the key to every screen in the game. How many there are and which ones: `werk\logs\coverage.md`.

## The test binary is not the game binary

`src/main.cpp` and `src/messages.cpp` are removed from the object library the two binaries share and added back only to the game executable (`src/CMakeLists.txt`). The test binary links `tests/fake_messages.cpp` instead, whose `add_msg` does nothing at all. **Anything written into `messages.cpp` can never be executed by a test**, and a test that calls `add_msg` and asserts on the outcome is asserting about the stub — it will pass whatever the real code does. Keep anything that must be tested in a translation unit the shared library keeps, and leave `messages.cpp` a single call into it.

## Other verified properties

- **`ESC` is `main_menu`, not cancel.** It opens a screen where the play context does not apply, so any key pressed after it goes into that menu. Do not use it to interrupt an activity when testing.
- **The debug log answers what the game does, not when the layer is alive.** It records the game's own Lua coming online at program start and nothing about the layer's state, so it cannot tell whether the layer was loaded when a key was pressed. The layer answers that itself, with its word on the opening screen and its two loading words around a world; a report of a dead key is only meaningful once it is known which side of those the key was on.
- **`debugmsg` is a blocking screen with a keyboard of its own, and `on_debugmsg` is the only way in.** It is the game's own error report — and the way a Lua error in this layer surfaces, from anywhere in the source. It does not use `query_popup`, so `on_query_popup` never fires; it draws straight to the screen through `ui_adaptor` and then reads raw input with `inp_mngr.get_input_event()`, so `on_action` never fires either, and its `input_context` exists only on Android. It accepts space, `i` and `c` and swallows everything else. **So no command of ours can be reached while it is up, and it cannot be given a key of its own** — whatever a report has to say, it has to be said in the one firing.
- **Diagnose a silent chain with a beacon, not by pressing harder.** A temporary `std::ofstream` writing to an absolute path under `werk\logs\`, placed at each link of the chain, separates "the mod never ran", "the key never arrived" and "the speech failed" in a single keypress. Remove it once the audible check passes.
- **Errors are contained, with one caveat.** Lua calls are wrapped in try/catch and reported via `debugmsg` (`src/catalua.cpp`). The catch is on `std::runtime_error`, not `...`. `sol::error` derives from it, so ordinary Lua errors are caught. Anything else escapes. Treat containment as true in practice, not as a guarantee.
- **Registering a command is idempotent; registering a hook is not.** Re-registering an existing action id replaces the entry, but `game.add_hook` appends without ever replacing, so loading the layer a second time into a live state would double every hook and say everything twice. **There is no hot reload; a Lua change costs a restart** — see `Running and tuning the game on this machine`.
- **Per-turn hooks exist.** `on_creature_do_turn` fires per monster and per NPC each turn (`src/game.cpp`) with the creature in `params`; also `on_monster_do_turn`, `on_npc_do_turn`. Only fired when hooks are registered, so free when unused. Usable for proximity alerts without polling — but they fire _per creature_, so aggregate rather than announce per call.
- **Keybindings come from `data/raw` and the user config only** (`input_manager::init` in `src/input.cpp`), never from a mod folder and never from `data/access`. Ours live in `data/raw/keybindings/bn_access.json`, a file upstream does not have, so it never conflicts.
- **Binding precedence: the user config wins, and a later file replaces rather than merges.** `data/raw` is walked first and the user config after, both in `input_manager::init`, and each load assigns the whole event list rather than merging into it. So a mod file cannot add a key to an existing action — it loads before upstream's and would be overwritten, and declaring the whole set means keeping a copy of upstream's bindings that rots. **Anything rebinding an action the game already owns belongs in the user config, which ships with the release.**
- **The map memory has two forms and the game fills exactly one of them.** The tileset renderer writes a tile name, the text display writes a symbol — so a game played without a tileset, which is what this project runs, memorises symbols and no tiles at all. Asking about the tile alone answers "never seen" for every square she has ever walked. Ask both, as the game's own `has_memory_at` does; `cata::access::remembers_square` is that question, and everything that reports the world goes through `knows_square` beside it.
- **The layer has nowhere to persist a preference, and needs none yet.** `game.mod_storage` belongs to the mod system and went with it; a mod's storage survives saves for free, ours does not exist. Build one only when something has to be remembered, and build it as a binding rather than by becoming a mod again.

# BUILDING

Everything lives under `C:\Users\radix\Documents\BN-access`: this document and `speel.cmd` at the root, the clone in `Cataclysm-BN\`, everything of ours in `werk\`, logs in `werk\logs\`. **Our folder is `werk`, not `tools`** — the clone has a `tools` of its own, which is upstream's and stays untouched. **There are two git repositories, not one**: the project root holds this document and `werk\`, the clone holds the fork, and a session's work is usually a commit in each. A commit in the clone that forgets this file leaves the next session reading a plan for work that is already done.

**One command: `werk\build.cmd [configure|compile|test] [jobs]`.** No argument runs all three. It calls `vcvars64.bat`, sets `VCPKG_ROOT`, writes full output to `werk\logs\` and a short plain-text summary to `werk\logs\build-result.txt` — on success only "STAGE x: OK", on failure only the error lines. The configure flags follow `.github/workflows/build.yml`, the flags BN's own CI uses for Windows MSVC: Ninja, `MSVC.cmake` as toolchain, `windows-tiles-sounds-x64-msvc.cmake` as project include, `x64-windows-static`, tiles and sound on, `RelWithDebInfo` with tests.

**The optimisation flags are part of the recipe, and one of them is deliberately absent.** `build.cmd` passes `/Oi /O2 /Ob2 /DNDEBUG /arch:AVX2` as the RelWithDebInfo flags. `/Ob2` lets the compiler decide what to inline where CMake's default `/Ob1` inlines only what is marked; `/arch:AVX2` fits this laptop, which has AVX2 and no AVX-512.

**Never add `/GL`, and never restore `/LTCG`.** Whole-program optimisation moves code generation out of the compiler and into the linker, which is exactly where upstream's per-file guard against an MSVC crash in the Lua binding sources — `/Od /Ob0`, set in the same commit that removed the precompiled header — does not reach. The link then dies inside `catalua_bindings_creature.cpp`: three times as `C1002: compiler is out of heap space in pass 2` at about 6 GB, and once, with a single code generator thread, as `C1001: internal compiler error` after growing to 59 GB. `C1001` is a defect in MSVC and not something this project can fix. It bought nothing that was ever measured, and **the published build never used it**, so leaving it out also makes the local build behave like the release. **Keep `build-scripts/MSVC.cmake` identical to upstream**, which is what that costs and why it is not on the conflict surface.

**Linking takes minutes and needs no special handling.** A job pool of depth one for the link rule is configured, so Ninja cannot start both links at once whatever the job count — **`build.cmd compile` needs no argument**, and passing `1` only slows the compiling down. Verify after configuring: `rules.ninja` must declare `pool link_pool` and the link edges in `build.ninja` must carry `pool = link_pool`.

**A fixed page file size takes effect only after a restart, and growth on demand does not stand in for it.** Measured: with the fixed 32 GB size set but not yet adopted, the commit limit was 33.9 GB and a large allocation failed rather than waiting for Windows to grow the file; after a restart the limit was 63.6 GB. `werk\wisselbestand.ps1` sets it and needs administrator rights, so it needs the owner's click.

**ccache is wired, and pays for the second build rather than the one after a flag change** — a changed flag is a changed cache key, so that is a full recompile by definition, and **so is a merge that moves headers**: every object then has a new key and the cache gives nothing at all. BN enables ccache itself (option `CATA_CCACHE`, `find_program`), but that search covers `PATH` only and winget installs off `PATH`, so `build.cmd` locates `ccache.exe` under the winget package tree and adds its folder. **Cache size lives in ccache's own config** — `%LOCALAPPDATA%\ccache\ccache.conf`, set with `ccache --set-config max_size=20G` — not in an environment variable, and **it has been found back at the 5 GB default without anyone changing it**, which is too small to hold a full rebuild of both binaries and quietly costs the next build as well. **Read the size line in `ccache --show-stats` before a long rebuild** rather than assuming it. Confirm it runs through the call count there, not the hit count: **zero hits during a build is normal**, because Ninja only invokes the compiler for files whose input genuinely changed.

**Parallelism is capped at 4 on purpose.** Ninja defaults to cores+2, which here means ten MSVC processes; the `catalua_bindings_*.cpp` units instantiate sol2 templates and take gigabytes each. Ten at once exhausts 32 GB and freezes the laptop. At four jobs memory never fell below about 18 GB free. **The CPU is the other limit**: ccache wraps every compile, so four jobs are eight processes on eight cores, measured at 96% CPU. **Start long builds from a shell that lowers itself first**: `(Get-Process -Id $PID).PriorityClass = 'BelowNormal'`, then `build.cmd`. Windows hands that class to every child, so Ninja, ccache and each `cl` run below normal from the start; changing processes afterwards only catches what starts later. During a 49-minute build this way the owner found the laptop fully usable.

**Measured on this machine.** Configure including all vcpkg dependencies: six and a half minutes; with those already built, 20 seconds. Full compile of both binaries from an empty cache, including both links: 49 minutes at four jobs and below-normal priority. A fresh build folder is 11 GB, of which 6.3 GB objects, 2.2 GB PDBs and 1.4 GB vcpkg; the previous one had grown to 18 GB. Deleting it returns that space at the cost of this full build — **and an upstream merge that moves headers costs exactly that**, since every object gets a new cache key. Full Catch2 suite: 17.5 minutes. **The `[lua]` filtered run takes about half a minute**, most of it data loading. **That filter is every test tagged `[lua]`, not ours** — about a third are ours and the rest are upstream's Lua tests, which is exactly why it is the right local check.

**A new file under `src/` is picked up automatically; a new file under `tests/` is not.** `src/CMakeLists.txt` globs with `CONFIGURE_DEPENDS`, `tests/CMakeLists.txt` globs without it, so a new test file is silently absent until `build.cmd configure` runs — about 20 seconds with vcpkg already built.

**Precompiled headers are off for the game library on purpose — do not turn them back on.** The tests target still uses one and `pch/main-pch.hpp` still sits in the tree, so the setup looks half-finished; it is not. Upstream removed it in commit `020c1b9797`, "avoid Windows MSVC Lua binding compiler crash", in the same change that split the largest binding file in three and added `/Ob0` to the binding sources. That is our exact configuration, and the crash sat in exactly the files where our own bindings go. Reopen only with the crashing translation unit identified first.

**A build reports success while producing nothing if the game is running.** Windows locks a running executable, the linker fails, and `cmake --build` returns -1 — which `if errorlevel 1` reads as success, because that tests for one or more. `build.cmd` compares against zero instead. **Close the game before building**, and if a change seems to have no effect, check the executable's timestamp before believing anything else.

**A live `cata_test-tiles.exe` breaks the next thing twice over, so count the processes before diagnosing anything.** A run started from a call that then timed out keeps going and holds the binary, so the next compile ends in `LNK1104`; `WerFault.exe` may be attached, which makes `taskkill` answer "access denied" until WerFault is killed first. And a second run started while one is live cannot clear `test_user_dir`, logs `remove_tree ... used by another process` before the first case runs, and ends in "treating result as failure due to error logged during initialization" while every case passed. **An interrupted reply has already dispatched its own run**, which is the usual way two exist at once. **Start long test runs detached, writing to a file, and poll.**

**A compile can fail after linking.** Both binaries can exist and be current while `build.cmd` reports `STAGE compile: FAILED` — the post-link step copying the Windows Lavapipe runtime has failed once and then succeeded on an unchanged rerun. Check timestamps, rerun `build.cmd compile` first. Because the script exits on a failed compile, a spurious failure here also skips the test stage.

**Run a filtered test from the clone root**, not from the build folder: the binary reads `test_user_dir/config/keybindings.json` relative to the working directory and aborts without it. `out/build/windows-tiles-sounds-x64-msvc/tests/cata_test-tiles.exe "[lua]"` from `Cataclysm-BN\` is the loop.

**A sol2 line about an exception thrown on the C++ side is a passing test, not a warning.** Upstream's `lua_called_cpp_func_throws` throws one across the Lua boundary on purpose and then asserts it arrived; sol2 prints it on the way past. A green run says so too — read the count, not the noise.

**Upstream's tests fail intermittently, and it is theirs, not ours.** Their umbrella issue #3146 says it plainly: tests share global systems, which produces semi-random failures through cross-contamination. **So a red run is not evidence of a regression in our work.** Read which test failed first: **ours are the files named after the firing points** — see `ARCHITECTURE` — plus `tts_test`, `access_layer_test`, `access_zone_test`, `hook_state_cache_test`, `prompt_speech_test` and the `[lua]` cases, and those are deterministic. **One of theirs can fail as a segmentation fault rather than an assertion**, which aborts the run where it stands and hides every case after it — a `[lua]` run has ended after fourteen cases that way and then passed all 131 unchanged on the next attempt. **So run it again before diagnosing anything**, and check a suspect case on its own: passing alone while failing in the suite is the cross-contamination class and not a defect in the change.

**The combat balance case that fails is a seed, not a regression, and this is the one to recognise.** `tests/effective_dps_test.cpp` compares a 250-trial simulation against the `effective_dps` estimate within a 35% band. For the smoker zombie with the clumsy sword the ratio sits at 0.652 against a floor of 0.65, so the estimate is systematically optimistic against that monster and the case decides by whatever ran before it: 8.484 in isolation and passing, 8.435 in the full suite and failing, 8.270 on a CI shard. **The outcome depends on state earlier tests leave in the same process, not on the seed alone**, so running the `[dps]` filter alone proves nothing — reproduce with the full suite and the seed the run printed. Reported as cataclysmbn/Cataclysm-BN#10066; Windows only, Linux passes it.

**A red test that is upstream's own is theirs to fix, and waiting is the answer** — not reporting it, not skipping the case, and nothing of hers waits on it since she plays the local build. **While any of their cases is red, every push of ours fails the Windows job and publishes no `experimental` build.** **Read upstream's `cache-warm-builds` job to see whether their main is green** — that is the one running the suite, while their release build passes `run-tests` false and is green whatever the tests do. **Whether the layer is involved at all is settled by emptying `data/access/main.lua` and running the case again.**

**GitHub builds, tests and publishes the fork.** `.github/workflows/bn-access-ci.yml` is ours; every upstream workflow is disabled except the reusable `build.yml` ours calls. One branch, `main`. Every push builds Windows MSVC and Linux, runs the full C++ suite on both, and writes the packaged Windows build into the rolling `experimental` release — **one fixed address always holding the newest playable build, which is the deliverable.** Publishing happens only after tests pass. A second job runs the Lua analyser against the annotations that build generated and reports our findings only; **it reports rather than gates**, because a broken `require` stops the layer loading and the C++ suite already fails on that first. **A failed shard is run once more inside the run, and a failed job once more after it.** `build-scripts/bn_access_shard_retry.ts` is ours, and upstream's shard runner calls it in one line: a shard that fails runs again as a fresh process with a fresh seed, one that fails twice fails the build, and the log says which of the two happened, so a shard that keeps needing a retry stays visible. That is what handles the flaky class, because it re-runs the tests that failed rather than the whole job. `bn-access-retry.yml` reruns failed jobs once behind it, for a failure that outlives the shard; a genuine failure fails both times. **A failure in the Linux job does not cost the playable build** — Linux only proves the speech code still compiles off Windows. **That holds for the matrix entry and not for the job before it**: upstream's build file runs a shader-artifact job on Linux that builds its vcpkg dependencies first, every matrix entry waits on it, and when it fails nothing is compiled, tested or published at all. It fails on other people's servers — a 502 from `gitlab.freedesktop.org` while vcpkg fetched the dbus source has done it — so **read the failed log before suspecting the fork**: `gh run view <id> --log-failed` and look for a download that did not answer. The retry workflow reruns once and an outage outliving that rerun still costs the run, which is why the rolling release can be older than the newest green commit. Reach for `gh run rerun <id> --failed` once the outside server answers again. **Pass `--repo aradix85/Cataclysm-BN` to every `gh` call**, because the clone has two remotes and `gh` resolves to `upstream`.

Three things about that recipe will otherwise be diagnosed a second time. The build job needs `permissions: contents: write` or the release upload is refused. Every matrix entry must produce a package, or the release step fails looking for a file that was never made — and one failing entry cancels the others. And the Deno setup action fails in its own cleanup when nothing in the job used Deno, which marks a healthy build as failed, so the registry mods are bundled on every run to keep it quiet.

**`bn-access-upstream-merge.yml` watches upstream so that returning to the fork is not an investigation.** Weekly, and on demand from the Actions tab. It says how far behind the fork is, which files both sides have changed since the last merge — computed from the merge range, so it cannot go stale — what upstream's own runs concluded at that commit, and, when it merges cleanly, the drift on the merged tree. Then it tries the merge on a branch: clean, it force-pushes `upstream-merge` and opens or updates a pull request; conflicted, it aborts and opens or updates an issue naming the files. **Issues are switched off on the fork, so a conflicting week shows instead as a failed run** whose last step says so; the survey is in the run's summary, and `git merge-tree --write-tree --name-only origin/main upstream/main` names the conflicting files without touching the working tree. **It never pushes to `main` and never claims the merge is good.** The branch carries no build, and that is the token rather than a choice: GitHub starts no workflow for a push or a pull request made with `GITHUB_TOKEN`, so building it needs a person's push or a personal access token nobody has decided to add. **Recording the reviewed drift stays a step in the session**, since accepting a baseline is a judgement and not something a schedule should make. **A schedule goes dormant, and that is GitHub's rule rather than a fault**: it runs only once the file is on `main`, a fork keeps its schedules off until someone enables them, and a public repository with sixty days of no activity has them disabled again. `gh workflow enable "upstream watch"` turns it back on and `gh workflow run "upstream watch"` starts one by hand, both from the command line — **which is what to do after a long gap rather than waiting for a Monday**, since the answer takes a minute either way. Any commit sets the sixty days back to zero.
**Do not watch a run. Push, and read the outcome at the start of the next session.** `concurrency` with `cancel-in-progress` is set, so a newer push kills an older run. **A shard can hang on the Windows runner**: in one run eight of nine shards finished within twenty minutes and one produced no output for fifty. Cancelling makes the log readable — logs of a running job are not retrievable — and the "Finished shard NN" lines then say which shard never returned.

**Merge upstream as often as you like; the merge is free. The local rebuild is the whole cost, and it can wait.** Merging takes seconds; a merge that touches a widely included header — `type_id.h` is included by 364 files — costs a rebuild of about an hour. **Rebuild locally when a C++ step starts, not because a merge landed**, and during a Lua phase not at all. Before merging, a diff of the merge range restricted to `src/*.h` says whether the rebuild is a relink or an hour. **After merging, run `werk\coverage.py` and read the drift lines**, then record the reviewed result with `--record` in the merge commit. **A hook of ours is drift too**, so record in the commit that adds a firing point as well, or the next run reports our own work as something the layer does not speak. **Upstream moves files between folders regularly** — `vehicle`, `weather`, `magic`, `map`, `mapgen`, `travel`, `overmap` and `reload` all have subfolders of their own — and a rename breaks the fork's own includes while leaving upstream's correct, so after such a merge check that every `#include "..."` in our files still resolves to a path that exists, in one pass, instead of meeting them one failed compile at a time. **A move is usually reformatted in the same change**, since a subfolder is formatted by `clang-format` and the top level by `astyle`, so git does not pair the two files and a file the fork touches arrives as a modify/delete conflict. Resolve it by putting the fork's lines into upstream's moved copy, in its new style, and deleting the old path; `git diff $(git merge-base HEAD upstream/main) HEAD -- <old path>` shows exactly which lines those are.

## Running and tuning the game on this machine

**Run the game with `speel.cmd` at the project root**, which does nothing but call `werk\start-spel.ps1`. The built executable has no data folder beside it, so the clone must be the working directory or no mod loads; the script does that, forces the window to the foreground and says in plain words whether that succeeded, and refuses to start a second copy. A window that never takes keyboard focus is silent and indistinguishable from broken code, which is why focus is forced rather than left to the window mode.

**That refusal has to be a named mutex, and the work is in PowerShell for that reason alone.** Two instances share one save folder, and the game's own start-up write test uses one fixed file name in the clone, so simultaneous copies delete each other's test file and one dies with a fatal **"Can't write to ./"** — which reads like a broken build, a full disk or a permission problem and is none of them. A marker file cannot guard it: a copy arriving ten milliseconds later sees no game running yet, concludes the marker is stale and takes it over. A mutex has no such hole and disappears with the process, killed or not. **A bouncing key is why copies arrive together at all** — see `Machine and toolchain`.

**Getting into a game needs no screen.** The main menu uses letter hotkeys: `n` opens New Game in `main_menu::opening_screen`, and the submenu offers `Play Now!` and `Play Now! (default scenario)`. Both set `character_type::NOW` / `FULL_RANDOM`, for which `src/newcharacter.cpp` sets `interactive = false`, so character creation is skipped, and `pick_world( show_prompt = false, empty_only = true )` suppresses the world prompt. **`n` then `o` produces a playable character**, and **loading takes about twenty seconds**, which is why the layer says one word at the start of that wait and one at the end.

**A Lua change is answered by a restart, and there is no shortcut.** `gapi.reload_lua_code` reloads the mod scripts into the world's state and not `data/access`, and `game.add_hook` appends rather than replaces, so loading the layer into a live state a second time would double every hook. So the loop is: close the game, edit, `speel.cmd`. **Wording on the opening screen costs only the program start; wording inside a world costs a world load on top of it**, so settle everything on the opening screen before starting one, and take a list of changes into a single restart rather than one change per restart.

**`werk\opties.py` sets the game options and verifies its own work.** Run it with the game closed; it edits `config\options.json` in place, keeps a copy at `werk\opties-bewaard.json`, and reads the file back. It turns off tiles and overmap tiles (no tileset to load and far less drawing), the pixel minimap, and every animation with its frame delay, because each drawn frame is a pause before the next keypress is read; music goes to zero because the game played over her speech; sound effects stay on at her request; and **`USE_LANG` is set, because an empty value opens the game on a silent language picker** — a `uilist` that announces nothing and swallows every key.

**Never rebuild `options.json` from parsed JSON with PowerShell.** `Set-Content -Encoding UTF8` writes a BOM, the game answers `tried to start array, but found '?'`, discards every setting and starts from defaults, the silent language picker included. The evidence is in the first lines of the game's own log for that session.

**The same BOM breaks every tool in the project folder, through `deno.jsonc`.** Deno walks up from wherever it runs, finds that file, and refuses to start on three invisible bytes: `Failed deserializing config file`, `Unexpected token on line 1 column 1`. It costs the formatter and the mod migration at once, and it reads as the tool being broken rather than as a file being wrong. **So write any file in this project with `python`, or with `Set-Content` and `-Encoding utf8NoBOM` where the shell has it** — Windows PowerShell 5.1 does not, which is the trap. To check: read the first three bytes and compare them against `EF BB BF`.

**`mods.py update` runs the game's own legacy-unit migration over each mod it installs, and a failure there is quiet.** It prints that the migration failed, that the mod still works and that its loading will warn — which is true and easy to read past, since the update itself reports success on the line after. The migration is `scripts/migrations/3312.migrate_legacy_unit.ts` in the clone, run through Deno, so a broken `deno.jsonc` fails it every time while the download succeeds. **Run it by hand over a mod folder to repair one**, and note that `update` will not do it for you afterwards: with the version already recorded there is nothing to update, so the migration is never reached again.

**`config\` is gitignored by upstream, so a merge cannot touch it** — the risk is losing it, not conflict, and the copy in `werk\` is the answer. **Nothing in it reaches another player**; shipping accessible defaults is a step in `THE PLAN`.

**Read `config/debug.log` from a running game.** The fork flushes every completed line, so a Lua error, a mod that failed to load or a hook that never fired is visible while she is still in the game. **This is the first instrument to reach for when something is silent**, before screenshots and before asking her anything. `crash.log` beside it holds addresses and no names. **The minidump is what answers, and `speel.cmd` keeps it**: the game overwrites both files on every crash, so each start moves any report into `werk\logs\crashes\` with the build date beside it. Read one with `llvm-symbolizer` against the executable, whose PDB sits beside it — the addresses need the runtime module base subtracted, which the debug log's own backtrace gives, and the linked image base added. **Against a different build the dump says nothing.**

**A character exists only after a clean exit, and a world lists none until then.** Leaving through `ESC` and save-and-quit writes `#<name>.sav` beside the `#<name>.sqlite3` the world already holds; `worldfactory::init` finds characters by scanning the folder for `.sav`, so a world whose folder holds only `.sqlite3` files lists nothing and the layer saying "no characters" there is right rather than a counting fault. Killing the game, or a crash on exit, loses that character outright. **So test saving by quitting through the menu and then reading the folder**, never by asking her what the load screen said.

**A world remembers the mod list it was made with, so a mod that stops existing breaks that world.** `save/<name>/mods.json` is authoritative, and an entry the game does not have stops the load on the error screen — silently, until the loading window under `SHARED FINDINGS` is fixed. **Check that file before suspecting the layer**, and edit the entry out rather than the world away. **A mod upstream retires is the exception**: `data/mods/replacements.json` names it, and `mod_manager::load_mods_list` drops it or swaps in its successor and rewrites `mods.json` without a word — so after a merge, compare that file against `config\default_mods.json`, since a hand-installed mod of hers can land on it and vanish from her world in silence.

**Windows itself is tuned too:** Defender excludes the project folder, `C:\vcpkg`, the toolchain and both game binaries, and the power plan is on top performance.

**Upstream publishes nightly binaries** (GitHub releases, daily). Useful for checking stock behaviour; useless for development, since the speech bridge is C++ inside the executable.

# ARCHITECTURE

**An index, not a description.** Every file below says what it is for and how it behaves in its own comments, and a header is faster to read than a paraphrase of one. What lives here is where things are, plus the constraints that are invisible in the code. Add a line when a file appears; do not restate a signature.

**`src/tts.{h,cpp}` — the speech bridge**, namespace `tts`. `output( text, prio )` is the entry point and reaches speech and braille together; `speak`/`braille` are single-channel on purpose. `recording_sink` is what a test swaps in — and is also the default sink in a test binary, so the suite speaks to nobody without any test arranging it. The Windows sink has two priorities, `normal` and `now`, and `now` is a cancel followed by a speak. There is no `next` and no SSML path, since P8 rules `next` out. `priority_from_int` answers `normal` for any value it does not know, so a script passing one keeps speaking instead of falling silent.

**The firing points, one file each, all namespace `cata`.** `messages_hook` (`on_add_msg`), `popup_hook` (`on_query_popup`), `move_hook` (`on_player_move_refused`), `debug_hook` (`on_debugmsg`), `ui_hook` (`on_uilist`), `inventory_hook` (`on_inventory`), `advanced_inventory_hook` (`on_advanced_inventory`), `keybindings_hook` (`on_keybindings`), `main_menu_hook` (`on_main_menu`), `overmap_hook` (`on_overmap`), `look_hook` (`on_look_around`), `nearby_hook` (`on_nearby_items`, `on_nearby_monsters`), `description_hook` (`on_description`), `morale_hook` (`on_morale`), `direction_hook` (`on_direction_prompt`), `play_hook` (`on_play_input`), `world_loading_hook` (`on_world_loading`), `lua_actions` (command dispatch and `on_action`). Each has a test file of the same name. What is not visible from the code:

- **`messages_hook` and `debug_hook` ignore nested calls**, so a handler that adds a message, or fails and is reported, cannot loop.
- **`popup_hook`, `ui_hook`, `inventory_hook`, `advanced_inventory_hook`, `keybindings_hook`, `main_menu_hook` and `overmap_hook` fire once per input round, not once per screen**, so moving the cursor fires again — which is why each Lua side keeps the previous state and says only what changed.
- **`inventory_hook` reads the active column and hands over the rows, not the selector**, for the reason `ui_hook` does: the mapping stays under test and only the one call line is uncovered. Two things about it are decisions rather than plumbing. **Category headings are left out of the rows**, so the position spoken with an item counts items; the game draws headings as rows and counting them would put every position out. And **each row carries where its item is** — `item::where()`, not which column drew it — because the screens that offer nearby items put a heading's direction into its name only when it is another square, so a pile at the player's own feet reads exactly like the pack it would go into.
- **`keybindings_hook` hands its screen over in `on_uilist`'s shape**, so one reading model answers both and the Lua side composes `menus.lua` rather than repeating it, into the same remembered state. **It also owns that screen's selection**, which upstream never had: the screen scrolled a window over the list, acted on a hotkey letter, and refused to scroll a list that already fits, so on most screens no arrow key moved anything and only the first row could be reached. `move_selection` and `clamp_selection` are the arithmetic, kept out of `display_menu` because that function draws and blocks and cannot be driven by a test. **Four params are that screen's alone** — whether letters are currently picking rows, the letter that picks the selected one, the three keys that start a change, and whether the selected row's key works on that screen only or across the game, which the screen draws in colour and says nowhere. Without them the list can be read and not used. The scope is read through `get_input_for_action`, since `get_action_attributes` is private to the input manager and reaching it would have cost a line of ours inside `display_menu`. Everything the screen asks after a row is picked is a `query_popup` and already speaks.
- **`ui_hook` takes the menu's fields rather than the menu**, because `uilist` refuses to be constructed in test mode; that keeps the mapping under test and leaves only the one call line in `src/ui.cpp` uncovered.
- **`advanced_inventory_hook` hands over the pair of places and the active pane's rows**, because that screen is the pair: items leave the pane holding the cursor and arrive in the other, and which is which is drawn as a colour. Three things about it are decisions rather than plumbing. **It does not fire while the screen is working through a move of its own**, when it takes no key and there is nothing to answer. **A row's heading is handed over only while the pane sorts by category**, which is the only time the screen draws headings; sorted any other way a heading would change with nearly every row. And **a row's square is handed over only while the pane shows all nine at once**, since aimed at one square the answer is the pane's own and already said.
- **`world_loading_hook` fires before the work rather than after it**, at the top of `game::setup`, which is the first thing that runs once a world is picked and is also the route a saved character takes. The state a world gets is built by the load it would announce, so only a state that outlives a world can answer this one — which is why the layer registers it at boot only.
- **`overmap_hook` drops the rounds the input layer answers with a sentinel, and that is not an optimisation**: the overmap waits for input with a timeout so that it can blink, so it completes a round several times a second whatever the player does, and each one would ask the buffer for the same description and the city it lies near. An empty action is not one of those — it is the screen opening, the one firing that has to speak. Mouse edge scrolling moves the cursor on exactly the rounds this drops. Three more things about it are decisions rather than plumbing. **It hands over the place named rather than the tile**, because the terrain's own type is bound and `oter_t` is not, so the name the screen prints is unreachable from Lua; the two branches the sidebar chooses between are reproduced there, which is the one place in the layer that copies the screen's reasoning instead of reading a value off it. **A route is reported only while the previewed path leads to the tile under the cursor** — the player keeps one preview at a time, and reporting it against another tile answers a question nobody asked. And **a note is handed over without its symbol and colour prefix**, stripped by the game's own parser through `overmap_ui::get_note_display_info` rather than by a second one of ours.
- **`play_hook` carries nothing, and the moment is the whole message**: it fires at the top of `game::get_player_input`, where the world is about to read a key and therefore where every screen in the game has just stopped answering them. **One firing answers all of them**, which is why it is not a line at the bottom of each screen's own loop. It fires once per action rather than once per turn, since that function's own waiting loops for weather and text animation run below the call; and the activity poll does not fire it, because nothing closes there and the world already has the keyboard.
- **`look_hook` hands over the square and how much of it can be made out, and nothing else**, because everything else the screen prints about a square script can already reach: terrain and furniture through the map, the creature through `gapi`, the sound and the region name through `perception`. The visibility is the exception and the reason the hook exists — that is F3, where a mechanic that works is invisible to the player. **It is silent unless the screen is showing its info panel**: the same function is the cursor for marking out a zone and for dragging one, and in those shapes the caller draws its own window and a dragged zone has no single square to answer about. Sentinels are dropped, since that loop takes a timeout for the pixel minimap and for edge scrolling.
- **`nearby_hook` hands a row's square over as an offset from the player**, which is what the list itself stores and what the layer turns into a bearing; the screen draws a trail to the selection and prints no direction anywhere, so this is the one thing it never says. **Headings are not rows**: the screen inserts one above each group and counts it in its own cursor, so a position taken from that cursor would drift out by one per group passed. **It answers both tabs of that screen** — the items lying about and the creatures standing about — through two hooks with identical params, so one reading model serves both; a creature's row carries how it stands towards her, which the screen draws as a colour and a name does not say. **Each fires through a `run_hooks` that spells its own name out**, because `werk\coverage.py` finds a firing point by that literal and a hook fired through a variable reads to it as gone.
- **`description_hook` recomputes what the screen shows rather than reading it**, because the screen builds its text inside its own redraw and keeps it nowhere. **An empty text is how "there is nothing of that kind here" arrives**: the screen has three sentences for that case which all say the same thing, so the wording is the layer's instead. **Which of the three is showing is passed as a word from the call site**, not as the enum's number, so a reorder upstream cannot silently change what the layer says.
- **`direction_hook` answers a prompt that is not a prompt.** `choose_direction` puts up a `static_popup` and runs an `input_context` of its own, so `on_query_popup` never fires there and no key of ours reaches it — whatever has to be known is said in that one firing. **A firing with an empty action is the prompt opening**; a later one means the previous key did not answer it, since any key that does ends the loop, so the Lua side says the question again and not the keys. Sentinels are dropped. The question is handed over in the game's own words without the "(Direction button)" the popup appends, since that is the screen's own way of saying what the layer says better.
- **`morale_hook` hands over every row rather than a selected one, because that screen has no selection to hand over.** It scrolls a window, and only when the list does not fit, which it usually does — so its arrow keys answer with nothing and no row below the first can be reached. **The reading position lives in the layer instead**, which is possible here and was not on the keybindings screen for one reason: no row here can be acted on, so a selection is a place in a reading rather than a thing the screen has to agree about. The screen's own scrolling is untouched, and the firing carries what the previous round answered so the Lua side knows where the reading moved to. **The mapping is a template** because the morale points are a type private to `player_morale`; it names that type nowhere, so a test drives it with points of its own. **The two group captions and the labels below the list are the game's own translated strings, asked for again rather than read off the screen**, since the screen words every row inside its own redraw and keeps it nowhere.
- **The `debugmsg` call line is the only part of the layer no test covers**: `realDebugmsg` returns early in test mode and the screen needs a curses window the test binary never creates.

**`src/access_places.{h,cpp}` — how a place is named**, namespace `cata::access`. Two namings, both the game's own: the region a square belongs to, which is what `game::look_around`'s window prints above it and what is short enough to say while walking, and the overmap sidebar's fuller description with the nearest city. Neither is reachable from Lua by any other route, since `oter_t` has no usertype at all. The map-square overload projects up to overmap scale here rather than in script, because script cannot hold a coordinate of that scale in a form the bindings take back.

**`src/access_zone.{h,cpp}` — the place as a whole**, namespace `cata::access`. A region tile is always 24 squares, but a place spans several under one name, and nothing in the game says how far it runs: `zone_around_player` walks the neighbours carrying the same name, bounded at four tiles each way, and reports how far it reaches from her against how far the **map memory** says she has been. That difference is the unexplored part, and it is the only thing here no screen answers. `exits_in_zone` lists every door and staircase inside it that she knows of, nearest first. `known_places` is the game's own overmap search **inverted** — it counts the kinds of place she has seen and says where the nearest of each lies, because searching needs a name typed and a name cannot be typed by someone who has never been told the place exists. It draws on the same stock as that search, one region block and seen tiles only, so the two can never disagree about a world she cannot check by looking. **All three are filtered by what she could know**, because the map holds every door in a building and answering with one behind an unentered wall would be playing the game for her rather than reading it to her. **`knows_square` and `remembers_square` are that filter and live here**, asked by everything in the layer that reports the world; the memory trap they close is under `SHARED FINDINGS`. Tests in `tests/access_zone_test.cpp`.

**`src/access_layer.{h,cpp}` — who loads the layer**, namespace `cata::access`. A state the fork owns, built at program start, plus `load_into` for each world's state. **Which of the two lives a state is, is passed to `load_into` rather than worked out from the state's identity**, so both are reachable from a test. `resolve_hook_state` in `src/catalua.cpp` picks exactly one state per hook, so nothing is said twice. Tests in `tests/access_layer_test.cpp`.

**Bindings of ours:** `src/catalua_bindings_input.cpp` (`InputContext`) and `src/catalua_bindings_perception.cpp` (the `perception` library — everything the game's own look-around window shows). Two traps: `input_context::is_action_registered` and its copy constructor compile only on Android, so go through `get_registered_actions_copy()`; and **a library must end in `luna::finalize_lib`** or every call aborts at runtime. A context built in Lua is a different object from the main loop's, so registering in it does not make a key work in play.

**`data/access/` — the layer, all of it Lua.** `main.lua` is wiring only: hooks, the one registered command, the loading words, and the two impure helpers that touch `gapi`. Everything it decides lives in `lib/`, pure, so it is asserted without a game: `text`, `messages`, `prompts`, `menus`, `inventory`, `advanced_inventory`, `keybindings`, `opening`, `overmap`, `look`, `nearby`, `describe`, `direction`, `exits`, `morale`, `zone`, `play`, `errors`, `movement`, `bearing`, `surroundings`, and `speech` wrapping the bindings. **`lib/speech.lua` is the only place the layer touches `gapi` for speech**, and its `prio` argument must be omitted rather than passed as nil, since the bindings are overloaded on arity. **`opening.lua`, `inventory.lua`, `advanced_inventory.lua` and `keybindings.lua` compose `menus.lua` rather than repeating it**, which is what keeps one reading model for every list. **`overmap.lua` does not, because a place is not a list** — it has no count and no position among entries — but it keeps that model's order, and a bearing where a menu says a position. **One variable holds whatever screen is on top**, since whichever holds the keyboard is the only one that can, so a state belonging to another screen arrives on the way back and has to read as an arrival; `overmap.lua` recognises its own by a `screen` field, and the modules composing `menus.lua` by the title comparison the model already makes.

**Tests.** `tests/prompt_speech_test.cpp` holds the bridge-side cases and parses every script the layer loads, found by walking `data/access` rather than from a list, so a module added to the layer is covered by having been written. Everything else about the layer's own logic goes in `tests/lua/bn_access/` — see `Testing is not optional`. `tests/lua_hook_helpers.h` pushes a hook entry backed by a C++ callable and removes it on scope exit, and empties a hook list for a case that needs one unregistered.

# THE PLAN

Eleven phases. **A phase is finished when its milestone is met**, not when its code compiles and not when its screens emit strings; what meeting one means is under `THE GOAL`. Take one step at a time from the phase at the front; `CURRENT` always holds exactly one.

**The numbering is the order the work is done in, and nothing is pulled ahead of it.** Where one phase cannot be met before another, the numbering is that dependency; where nothing depends on anything, it is her priority, and **hers is the deciding vote** — `Phase 6` is ahead of the rest of `Phase 4` and of `Phase 5` for exactly that reason, since she met its blank first screen in play. That is also why `Phase 6` sits where it does at all: nothing blocks beginning deliberately, and she has been playing without that choice since the beginning. `Phase 9`'s building screens are the tempting exception to the rule and are not one: the base they serve cannot be reached or staffed until the milestones of `Phase 3` and `Phase 8` are met, and construction zones already give her a way to build that is not tile by tile.

Three things run through every phase and are easy to forget:

**A key that jumps to a name is spoken with it.** Every heading on the opening screen, and every fixed entry under one, answers a letter as well as the arrow keys, and the game marks it in the name it draws — `Lo<a|A>d`, so Load answers `a` and not `l`. The layer hands the marked letter over beside the name and says it lowered, since both cases work and a capital costs a pitch change for nothing. Where the game marks none, none is said.

**The reading model is the same everywhere.** Every list the layer builds obeys P1 and P2: an overview line on opening, then one entry per keypress, name first, with its position and state. Nothing is said where a list wraps — the position spoken with the entry already says where the cursor landed. It is built and asserted in `menus.lua`; reuse it, because a second reading model is a bug.

**Prefer hooking the game's own screen over building a speech-native one.** The menu keeps its own behaviour, keys and order, so guides and the wiki keep applying to her, and the conflict surface stays one line. Build a speech-native screen only where the game's own loop cannot be reached, and say why in this file when you do.

## Phase 0 — The layer belongs to the fork, not to the mod list

## Phase 1 — Menus

## Phase 2 — Things in her hands

**Milestone: she picks up a named item from the ground, wields it, wears something, eats, reloads a gun, and drops what she does not want — without help and without counting keypresses.**

This is the daily loop, and **every verb in it is already reached through the game's own key and the game's own screen**. `g`, `w`, `W`, `E`, `r` and `d` each open a screen built on `inventory_selector`, which speaks through one firing point; the ammo list `r` reaches after it is a `uilist`, which speaks through another; refusals and results arrive as messages, and the confirmations — rotten food, an allergy, a theft — are prompts. A quantity changed in place, as partial reload does with the arrow keys, is spoken too, because an entry is re-spoken whenever it reads differently. **So the layer owns no verb here and needs no binding of its own: nothing is built for this milestone, and it is met by her using those screens.**

**Never give the layer a command for a verb the game already has a key for.** It spends key space the layer exists to save, and it reimplements a path whose details *are* the game's difficulty: `avatar_action::reload` alone redirects `RELOAD_AND_SHOOT` weapons, has separate paths for holsters and bandoliers, and ends with an activity whose move cost comes from `opt.moves()` plus a fouling penalty, so calling `item::reload` underneath it gives an instant free reload and breaks all three. Speak the game's screen instead.

**Every screen in this phase now speaks, the advanced inventory included** — see `DONE`. **Its wording is unjudged and is not to be chased**: the plain inventory covers the daily loop, so the screen is accessible and that is enough; the owner raises it herself if she wants more. The item detail screen is reached from the lists that speak; check what it already says before treating it as work.

## Phase 3 — Where she is and where she is going

**Milestone: she walks from her starting shelter to a named building on the overmap, finds its door, gets inside, and finds the stairs — using the game's own two screens.**

The overmap (`src/overmap/overmap_ui.cpp`, context `OVERMAP`) moves a cursor over named region tiles — house, forest, river — and `CHOOSE_DESTINATION` sends the character there on foot. Voicing these gives her the same world every other player has, with the same names and the same keys. **Do not invent a second navigation model.** The lists of items and monsters in view (`LIST_ITEMS`, `LIST_MONSTERS`) belong here too, and both now speak through hooks of ours.

**Every screen of this phase now speaks** — the overmap and its search, the look-around cursor, both tabs of the list of what is in view, and the description screen behind its describe key; see `DONE`. **What is left is her meeting them in play**, and that is the whole of what remains here. One thing inside that file is still silent and is not part of the milestone: the debug terrain placement, which has a context of its own. **Anything later that wants a place named in Lua has it**: `access_places` exposes both of the game's own namings, and `perception.area_name_at` is the one script can call.

**Ask, do not scan.** A room is ten squares across; reading every square to find a door is the exhaustion F5 names. The overview already answers "where are the ways out" in one line, and the same inversion covers stairs, windows and vehicles. Reading a specific square is for when the answer matters, not for finding things. **The eight neighbours are still unbuilt and may not be needed** — decide from what the completeness measure below says is missing, not from intuition.

## Phase 5 — Typing

**Milestone: she types a filter, a search term and a name, and hears every letter she has typed and every letter she deletes.**

**One step for every place it happens, because it is one class.** `string_input_popup` draws its own window and reads its own keys, and 166 sites in `src/` reach for it: the map's search term, the item list's filter, the advanced inventory's filter, the zone manager's filter and its name prompt, the auto-pickup rules, a profession name, a character's name. All of them are silent today, which means the letters go somewhere she cannot check and a typing mistake is invisible until the answer comes back wrong.

**Built once, where it is first met.** Beginning deliberately has five of these popups in one file, and the screens that make crafting and building bearable are filters over hundreds of rows — a list nobody can walk with the arrow keys alone. Doing it once here is what stops it being redone badly three times.

**It is silent for her although upstream's cursor positioning is in `string_input_popup.cpp`.** The filter key on the list of what is in view on `V` says nothing — not the field opening, not a letter typed. **The cursor route only works for a screen reader that is reading the window, and hers is asleep inside the game on purpose** — that is what the sleep add-on is for, and it is what stops NVDA reading the drawn screen over the layer. So the one mechanism upstream provides is the one mechanism she cannot use, and **typing has to be spoken by the layer or not at all**.

**One firing point, in `src/string_input_popup.cpp`**, and the question the wording has to settle is what a character-by-character channel says: the letter typed, the letter deleted, and what the field holds when it opens. `P1` and the echo problem meet here — a screen reader echoes what the keyboard sends in some setups, and saying it a second time is worse than silence, so **whether her own setup echoes is the first thing to establish before choosing the wording**.

## Phase 6 — Beginning deliberately

**World creation comes first inside this phase, by her judgement and because it comes first in the game.** She met it in play and it is blank: the screen `Create World` opens draws its own windows and says nothing at all, from the name field to the mod list to the confirmation. **From a clean install there is no way around it.** `Custom Character` picks a world first, and `worldfactory::pick_world` has three shortcuts: one world, take it; no worlds, go straight to making one with the prompt; prompt suppressed, take the first world with no characters in it. **So a fresh download with no world at all lands in that blank screen on the first choice a player makes**, walks its three tabs, and only then reaches character creation. The one way past it is `Play Now!`, which takes the choice away: a random character in a world whose mod list nobody was asked about. The game ships no world to fall back on — the Tutorial and Defence worlds are made on the spot and filtered out of the list. **The only thing that speaks there today is the abort question**, which is the wrong thing to be the only thing: it asks whether to stop something the player never heard start. **Measured rather than guessed** — `src/worldfactory.cpp`, four input contexts and no `uilist` anywhere in the file. `show_worldgen_tab_options`, `show_worldgen_tab_modselection` and `show_worldgen_tab_confirm` are the three tabs of making one; `MODMANAGER_DIALOG` binds seven keys in data and registers fifteen, `WORLDGEN_CONFIRM_DIALOG` three and seven, and the mod-list viewer runs on a plain `DEFAULT` context with up, down, confirm and quit. `PICK_WORLD_DIALOG` is the list of existing worlds. **The name field is a `string_input_popup`**, so a piece of `Phase 5` arrives here whichever order they are done in. Four `uilist` screens inside it already speak; the rest draw their own window and read their own keys, so it is eight firing points in the shape the inventory work already has — the wording in a file of ours under test, one call line in upstream's. **The largest single phase after making things, and the only large one nothing blocks.**

**Two things arrive with it rather than beside it.** Its five typing popups are `Phase 5`'s one class, so the typing firing point is built the first time this phase meets one — the world's name field — and not again. And the traits, professions and scenarios tabs are walls of description — this is the phase that meets the content question named at the end of this section, and the phase that has to settle how such text is read.

## Phase 9 — Making things

**Milestone: she crafts an item she chose from a category, builds one construction, and adds one part to a vehicle.**

**Construction and the zone screens come first within this phase.** The game already has both: a **construction blueprint zone** covers an area and is worked off by `ACT_MULTIPLE_CONSTRUCTION`, by an NPC or by the player, and the zone manager is on `Y` with construction on `*`. Neither screen is a `uilist`; `construction_menu` (`src/construction.cpp`) and `game::zones_manager` (`src/game.cpp`, context `ZONES_MANAGER`) draw their own window and wait for a key in their own loop, so **each needs a firing point of its own** — the same shape as the inventory screens, and the same split: the mapping in a file of ours under test, one call line in upstream's. **Building tile by tile is not the goal and never becomes it by being made audible**, which is why these two are the work rather than the construction cursor. **The strongest single addition here is a binding for `run_mapgen_update_func`**, which places a whole building in one act: the engine still has it with 81 users in the data, it is generic rather than an accessibility change, and it turns forty menu rounds into one. It belongs in Track A. Naming an area by ear rather than by pointing at two corners is a command of ours, and needs a zone binding first.

**Crafting is the deepest part of the game and the most expensive to open.** It has one hook (`on_craft_result`) and none on the browsing UI, so the craft screen is a phase-1-style job on a screen that is not a `uilist`. Construction needs the type exposure filed as issue #8828.

**Vehicle construction — design fixed early, because it decides what to ask for in Track A.** The inversion: from _go to a position, see what fits_ to _given the vehicle, what can I add and where_. Navigation over positions becomes filter over valid actions, and most of what a builder needs is not spatial: can I make it, do I have the materials, does it fit, do I have the skill. **Most of the data is already computed** — `veh_interact` keeps a `can_mount` vector of `vpart_info` pointers, rebuilt on every cursor move, and `can_potentially_install()` already calls `install_requirements().can_make_with_inventory(...)`, used as sort order rather than as a filter. Shape variants collapse via `vpart_shapes`; validity lives in `vehicle::can_mount()`. Slots are `structure`, `under`, `center`, `on_roof` — four, small enough to speak. **What is missing:** `can_mount` is private to `veh_interact` and `vpart_info` has no binding, which is issue **#8827**. `requirement_data` is fully bound already, and **`list_missing` is the key**: it answers "why not" with no text assembly of ours. **Three levels per P1:** what can be built now, flat and deduplicated; then where it fits, position as a property and bearings relative — "front row, left", not coordinates; then why not.

**What this phase builds is what `Phase 10` sends work to.** Everything about a base — what it is for, what the game already has, what left with the camps and what may not come back — lives there.

## Phase 10 — A place something depends on

**Milestone: she sends one follower on one errand, hears when they are due back, and reads what came of it.**

**Her reason, and it is the one that decides the design.** She does not want more of the game; she says the game has no shape — it widens for as long as she keeps adding zones and there is nothing to work towards. That is a gap in Bright Nights rather than in the speech layer, and it is the gap the deleted camps also aimed at.

**The test is what depends on it elsewhere, and that is narrower than a place that grows.** Asked which of the two "something to work towards" meant — the place getting better, or something hanging on it that she notices in the rest of the game — she chose the second without hesitation. **So growth is not the measure and never becomes it.** A base that gets larger, prettier or better stocked while nothing outside it changes is decoration, however much work went in and however well it speaks. What counts is the difference it makes somewhere she is not standing: range she did not have, a thing she could not make in the field, a place to put what she carries so she can carry more.

**So the errand has to come back with something that changes what she can do**, not merely with a report that it went well. A follower who returns having achieved a number is the decoration this test exists to catch; a follower who returns with what she could not have got herself is the thing being tested.

**Nearly all of it is Lua**, which is why it can be a phase rather than a fork. Zones designate, the game's own construction recipes build, followers are the labour, the calendar is the clock, and `uilist` is every screen — so it speaks the day it exists, with no C++ and no new firing point. **Two things are not Lua**: there is no site in the source where an NPC crafts a recipe, and trading requires her to be in the conversation. Expect one binding, and file it as Track A.

**It is a mod, and the camps are not coming back.** BN's own players voted the faction camp system away, 40 of 66 against keeping it, and **it stays deleted**. Their stated grounds are the brief for whatever replaces it: it was little used and half finished, it entangled the NPC code enough to block work on NPC behaviour, and its role overlapped the zone system, which is stabler and used by everyone. Reverting it also buys a mute screen, since it drew its own windows rather than using `uilist`, while the same thing built as a Lua mod with `uilist` menus speaks today for free.

**Why it added too little, in its own players' terms — each of these is a thing not to repeat:** it opened a separate interface running on mechanics of its own, beside the game rather than inside it; its blueprints were rigid and its expansions legal only on field terrain, which is full of trees and boulders; it was brittle against mods, where one added soldering iron broke dozens of camp recipes; and it pulled the player home instead of extending her range, so it cost exploration rather than paying for it — which is the same failure her own test names.

**What such a mod is for, and all it needs to be:** work a follower finishes on her own while the player is elsewhere, which is the one thing zones cannot do because the game simulates only what is near; standing tasks rather than an order repeated every time; and a marked place to send people to, including by radio. What that buys, in the terms the system used while it existed: missions that take days and return goods, a recipe crafted in batches by a companion, a larder measured in days rather than calories, a job priority per worker, trade that returns money and can be ambushed on the way, and fortification lines at map scale. **None of those needs a blueprint**, and the blueprints are what sank it.

**Two of them earn their place twice over, because they route around the screens `Phase 9` cannot make pleasant.** A craft delegated by name — "twenty bandages" — is one spoken order instead of a walk through a menu of hundreds of recipes, and a delegated trade is the same for the trade screen. So the mod is not only a base; it is a second route into the two deepest systems in the game. **It is also what makes building pay off**, since a delegated craft can require the tools and the workbench that a built workshop provides: she builds, and what she built widens what can be ordered.

**Most of what a base needs already exists in BN and is not to be built twice.** Zones already drive eleven kinds of NPC work — construction, farming, felling trees, making planks, fishing, mining, butchering, vehicle deconstruction, tidying, sorting loot, and fetching what a job needs — across about fifty loot categories, so storage that sorts itself is a list of zones rather than code. Defence is zones too: a retreat area, areas where they do and do not investigate sounds, a vehicle patrol zone, and a guard order in dialogue. A garage is a zone as well, since there is a vehicle repair zone. Healing is not a property of a place and need not become one: it follows rest, and a comfortable bed is the yardstick in the code.

**Build it out of what the game already has**: zones to designate, the game's own construction recipes and real items, followers as labour, the calendar as the clock, `uilist` for every screen. No currency of its own, no happiness meter, no second blueprint language — every input and output should be a thing the rest of the game already handles. **And what the place needs is read on demand rather than announced**, a ledger she asks for, because a base that interrupts her is the micromanagement this fork exists to avoid.

**Both ends of it are readable, and reading them is how the design is settled rather than guessed.** What BN had is in `git show 0e06d77c4c` — `src/basecamp.cpp` and `src/mission_companion.cpp` with their headers, the `data/json/mapgen/basecamps/` and `faction_buildings.json` blueprints, `TALK_FACTION_CAMP.json`, and `tests/basecamp_test.cpp`; `83efd766ba` took out the last references. **What it grew into is in DDA, which kept the system and has extended it by about half since the fork**: `src/faction_camp.cpp`, `src/mission_companion.cpp` and `doc/JSON/BASECAMP.md` in `CleverRaven/Cataclysm-DDA`, the last of which documents the blueprint format. Clone that shallow and sparse outside the project rather than adding a remote to the fork, and note that both projects are CC BY-SA, so it can be adapted and not only read. Hold either against what the engine still has, and the answer splits three ways: what a Lua mod can do with today's bindings, what it could do given one more binding, and what left the engine with the removal and is not coming back. **Say which of the three a piece is when the design is written**, since the third kind is the only real constraint and the other two are only work.

**Build the errand and nothing else, and let it answer the doubt she raised herself.** One follower, one task, a return time, an outcome. That is small enough to throw away and it decides everything after it: whether handing work over feels like playing, and whether what comes back is worth reading. **If it is not, a base gives this game no shape and the phase ends there** — and almost nothing is spent finding that out. **Not before `Phase 3` and `Phase 8`**: a place to send people to presupposes a map that can be crossed and people who answer.

## Running alongside the phases

These are not a phase. Each is triggered by a condition, and the condition is what to watch for.

**The key budget is smaller than it looks, and the game already solved it.** The F-row is the only free space, and a command with no key is not lost: the action menu on `RETURN` lists ours beside the game's own. **Give a key only to what is pressed dozens of times a session; leave the rest to that menu.** The layer owns two keys today — `F9` for where she is and what leads out, `F11` for the world at map scale — and **a key is not added unless she asks for one**; if she does, the chord questions under `Key space` are what to settle first. `F10` is free. **A key of ours reaches only ordinary play**, since a screen of the game answers its own keys alone; that is why the map's search and the layer's answer to it cannot share one.

**The scrollback is built the first time something is lost**, per P9 — not before, and not later. Lists and menus are where dropping, collapsing or delaying first becomes tempting, and nothing is dropped yet.

**A key of ours that answers nothing sounds exactly like a key that never arrived.** The layer's own commands — `F9`, `F11` and its entries in the action menu — are where that can happen; everything else speaks from a hook the game fires. Half of it is already covered, and better than elsewhere: a fault in Lua becomes the game's own debug report, and `lib/errors.lua` speaks that. The half left over is a handler that runs cleanly and says nothing, which is silence with no report behind it, and a player cannot tell it from a dead keyboard or a key the game never saw. **CK3-access and BoC-access answer it by counting**: the seam counts the utterances that leave it, a block around each handler notices when the count did not move, and it says one sentence carrying where, what and the way out — see `..\CK3-access\tools\nvda\speech.py`. Nothing here counts. It costs a counter in `lib/speech.lua` and a wrapper at the call sites, so settle it when a command is next added or reworked, and measure first whether a clean handler that says nothing actually occurs.

**The scores screen belongs to no phase, and that is deliberate.** `)` opens achievements, scores and kills — `src/scores_ui.cpp`, context `SCORES`, six commands of its own and no uilist — so it draws its own window like every screen of that shape and is silent. It answers what she has done rather than what she can do, so no milestone waits on it, and it is one firing point of a kind already built a dozen times whenever she asks for it.

**Shipping accessible defaults, before the fork goes on any list.** **What she judges is not what a stranger downloads**: she plays from the build folder, where `config\` is hers and nothing is bundled, and the package is the clone plus whatever the CI step adds. The mod list survives the gap — `mod_manager::refresh_mod_list` reads `config\default_mods.json` and falls back to `data/mods/default.json`, so a fresh download gets the fork's list and not hers. **The options survive it too.** `build-data/bn-access/options.json` holds six lines — language, tiles and pixel minimap off, animations and their delay off, music at zero — and one `install(FILES ... DESTINATION config)` in `CMakeLists.txt` puts it in the package, in the branch that has no prefix data dir, which is the portable layout the Windows zip uses and the folder the game reads `config\` from. **Proved end to end rather than reasoned about**: installed to a scratch prefix, run against a scratch user directory, started with no error in the log and all six values in place. A partial file is enough because `options_manager::deserialize` reads only `name` and `value` per entry and allows omitted members, so everything left out keeps the game's own default — which is why sound effects are left alone: they carry information and do not talk over speech. **Do not ship the owner's own `config\`**, which is gitignored because the game rewrites it on every exit, and which carries her keyboard, her braille display, her mod list and her taste.

**What else a stranger needs, and none of it exists yet:** a plain-language description of what the build does and what it does not; the key list; **what the default mod list decides on their behalf**, since a world bakes that list in permanently and changing it afterwards means a new world. Ours differs from upstream's in four entries, all removals, measured against `upstream/main` rather than remembered: `bn_lua`, because the layer is compiled in and is not a mod any more; `udp_redux`, a tileset; and `pride_flags` and `change_hairstyle`. Everything else is upstream's, so a returning BN player meets almost the same game and needs telling only which four are gone. **The owner's own hand-installed mods travel with the package where upstream's registry list already carries them, and that is upstream's list rather than a choice of ours** — `data/mods/external.json` is left exactly as upstream has it, so `Cata++` — which carries its Arcana and exotic-ammo interactions itself, in its own `mod_interactions` — and `MST Extra` are fetched at packaging time like every other entry, and only `fallout_combined` is hers alone and outside it. **Bundled is still not the same as enabled** — being in `mods\` only makes a mod choosable, while `data/mods/default.json` is what a new world starts with. **Do not trim that list**: the mods in it weigh about five megabytes against the soundpack's five hundred, and trimming takes choices away from whoever downloads this build while costing a hand-resolved conflict every time upstream adds a mod. Also needed: a statement that this is a custom executable, since none of it runs on stock BN until Track A lands upstream; and **a build note for anyone compiling it themselves**. The source is public — the fork is a public repository and GitHub attaches an archive to every release — but `werk\build.cmd` is written for this machine and its paths, so it is not the answer. The note names the optimisation flags as an optional extra rather than the recipe, since `/arch:AVX2` makes the binary refuse to start on an older processor.

**The speech library travels with the package, and no add-on or launcher is asked of anyone.** `src/tts.cpp` calls `LoadLibraryW` on `nvdaControllerClient.dll` by name and treats a failure as silence rather than as a crash, so a package without it starts, plays and says nothing — a failure that reads as the layer being broken and is really a missing file. It lives in `build-data/bn-access/`, x64 to match the only Windows build this fork makes, installed beside the executable, which is the first place Windows looks. LGPL 2.1, bundled unmodified, licence alongside. **Proved by running the packaged build against a scratch user directory and reading the loaded modules of the running process**, not by reasoning about the search order. **An NVDA add-on is not the mechanism** — the library is what her own setup uses.

**Completeness has two measures, and both are generated or named rather than guessed.** For a square: `game::print_all_tile_info` (`src/game.cpp`) is what the game itself shows — **terrain, fields, traps, creatures, vehicles, items, graffiti** when it is visible; the reason it cannot be seen when it is not, plus the creature anyway if infrared or a special sense reaches it; and **sound**, at any visibility, including from other z-levels. Terrain alone carries the region name, terrain and furniture with descriptions, move cost or impassable, concealment, cover, light level, signage, and what is below when there is no floor. **Anything on that list the layer never says does not exist for the player** — that is F3, and it is why the perception bindings were built. For the game as a whole: the verb table in `werk\logs\coverage.md`. Check a new report against those two rather than against intuition.

**The content systems are a third scale, and nobody has looked at them yet.** `data/json` declares over a hundred distinct types — recipes, item groups, talk topics, mutations, professions, overmap terrains, missions — and each is a body of text a player reads. The phases cover the screens that reach them; whether the text itself needs its own treatment (length, structure, what to speak first) is open, and the first phase that meets a wall of description is where to settle it.

Everything the step needs is in that phase: the four contexts, what each binds, and that the name field is a typing popup.

**The shape is the one built a dozen times** — one call line at the top of each input loop in upstream's file, the mapping in a file of ours under test, the wording composing `menus.lua`. `morale_hook` is the closest example to read first.

**What is left of `Phase 4` waits behind this**, and it is the character sheet on `@` — `character_display::disp_info` in `src/character_display.cpp`, context `PLAYER_INFO`, seven registered commands and no uilist: stats, encumbrance per part, traits, bionics, effects, skills, and speed with what is taking it away. **That screen already has a cursor**: `handle_player_display_action` keeps a `line` per tab and moves it on `UP` and `DOWN`, wrapping at both ends, while `NEXT_TAB` and `PREV_TAB` change tab, and each tab sets its own end — six rows for stats, one per body part for encumbrance, one per trait, bionic, effect or skill for the rest, with the skills tab skipping its header rows. **Two things are open there and both want the source**: each tab draws its rows inside its own redraw and keeps the text nowhere, so a row's words are recomputed the way `description_hook` does it; and a tab is a list of its own, so decide whether changing tab reads as arriving at a new list.

**A key of ours comes after both, and only for what those screens cannot do.** See `Phase 4`. It must reach the activity poll as well as the main loop — that is the state the answer is for, and the main loop does not run there. See `SHARED FINDINGS`.

**The morale screen is built and asserted and is not to be chased** — see `DONE`; what is left there is her meeting it in play.
